# Аналіз макета форми контактів

## Моє припущення до генерації

**Припущення:** у прототипі форми є **хоча б один** сценарій або текст, якого **немає** у зафіксованих AC/rules Дня 2 (`docs/contact-form-feature.md`).

**Як перевірити (повторювано):**

1. Відкрити [прототип](https://match-daily-72208179.figma.site/) і пройти стани: Empty, Filled & valid, Invalid phone, Wrong file type, File too large, Uploading, Success, Error; перевірити uk/en.
2. Зіставити з AC/rules у `contact-form-feature.md` (телефон, PDF до 5 МБ, тексти помилок, бек-офіс).
3. Заповнити таблицю **«Відсутні стани»** внизу цього документа (є / частково / немає).

**Критерій:** якщо в таблиці є рядок **«Частково»** або **«Додаткові стани…»** без AC — припущення **підтверджується**.

**Результат перевірки (листопад 2026):** **так** — зокрема Uploading, помилки PDF, **Remove attachment / Change file**, SLA «три робочі дні», **Full name** vs «Name» у специ, disabled submit при невалідному файлі; бек-офіс (база, 6 міс., 2 працівники) на макеті **не** показані.

## Мої спостереження до AI (2-3)

1. Не всі помилки на макеті збігаються з уже зафіксованими AC/rules Дня 2. Є додаткові стани — **Uploading**, **Wrong file type**, **File too large**, **Remove attachment / Видалити вкладення** (на заповненій формі з PDF; окремої картки в «Reference Overview» немає). **Full name** на макеті vs **Name** у специ — зміни вимог не було (**Q-18**).

2. Макет показує **SLA «три робочі дні»** на Success і **inline** подяку замість поточного RULE-13 (модальне «Ваш запит надіслано»). Кнопка **disabled**, поки форма невалідна, включно з невалідним PDF — цього немає в AC Дня 2 (**Q-15**, **Q-20**, **Q-21**, **Q-23**).

3. Текст **згоди** на макеті відрізняється від поточного сайту; бек-офіс (база, 6 міс., два працівники) на публічному UI **не** зображений — ризик узгодження з **Q-14**, **Q-26** і NFR Дня 2.

## Пункти для обговорення

- Зв’язок макету з **підтвердженими вимогами Дня 2**: обов’язковий телефон і PDF до 5 МБ узгоджуються з дизайном; **база, 6 місяців, два працівники** на макеті **не показані** — чи це лише бек-офіс.
- **Кнопка надсилання:** логіка «активна, коли всі обов’язкові поля заповнені» vs **блокування** через невалідний PDF (тип, розмір) — хто має пріоритет у продуктовому рішенні.
- **Успіх vs помилка:** успіх — **повноекранна** подяка; помилка — **форма лишається з даними**. Чи очікує фонд саме таку різницю в досвіді.
- **Довідник станів унизу** макету — демо для дизайнерів; чи не потрапляє на бойовий сайт.
- Відмінність тексту згоди від поточного сайту фонду — чи потрібна **узгоджена** редакція з юристом до релізу.
- **SLA «3 робочі дні»** — маркетингове формулювання чи зобов’язання з боку фонду для звітності.
- Чи **підтримуються** типи вкладень з підказки (партитури, пропозиції, листи дослідників) **без** окремих обмежень, окрім PDF і 5 МБ.
- **Remove attachment:** кнопка на макеті, але **немає в AC Дня 2** і **немає** окремої картки в «Reference Overview» — узгодити, чи входить у scope і чи описати в критеріях приймання.

## Приховані припущення

_(AI-аналіз за переглядом макету; не погоджено з замовником, якщо не зазначено інше.)_

1. Відвідувач **розуміє міжнародний формат** телефону з `+` і кодом країни без додаткової довідки, окрім прикладу `+380 44 279 18 40`.
2. Пробіли в номері телефону **дозволені** в полі вводу (як у прикладі); нормалізація до «єдиного формату» для фонду **не показана**.
3. **Є лише одне** поле вкладення; кілька PDF або заміна без повторного вибору файлу — через «Change file» або **видалення** через «Remove attachment» / «Видалити вкладення».
4. Перевірка PDF — за **розширенням / типом файлу** (.pdf), а не лише за вмістом (справжній PDF vs перейменований файл).
5. Ліміт **5 МБ** трактується як у копі макету («larger than 5 MB» для 7,4 MB) — **строго більше** 5, а не «не більше або дорівнює».
6. Під час **Uploading** користувач **не може** скасувати відправку або змінити поля — макет не показує іншої поведінки.
7. Після **Success** звернення **прийнято**; окремого кроку «ми ще обробляємо» немає.
8. Після **Error** дані **гарантовано збережені** в формі («Nothing you wrote was lost») для будь-якої технічної причини.
9. Чекбокс згоди — **обов’язковий** для активації надсилання так само, як і текстові поля з `*`.
10. Вкладення **не обов’язкове** для успішної відправки (стан «Filled & valid» і успіх можливі з PDF, але логіка «без файлу» у довіднику не винесена окремою карткою).
11. Помилки валідації **під полем**, а не в одному загальному банері (крім помилки відправки вгорі форми).
12. Англійські тексти з макету **мають** прямі українські відповідники з тим самим змістом (перемикач «Українська» на макеті є, повний перегляд станів uk **не показаний** у довіднику).
13. Поле «Supporting document» **не збирає** ім’я файлу з чутливих даних — лише показує назву на кшталт `archival-inquiry.pdf`.
14. Кнопка надсилання **вимкнена** на порожній формі до заповнення всіх обов’язкових полів — а не лише після натискання з подальшими помилками.
15. **Remove attachment** повертає форму до стану **без файлу**, і надсилання **дозволене** (файл необов’язковий) — на макеті кнопка є, поведінка після кліку **не показана** окремим станом.

## Відсутні стани

_(AI-аналіз: стани з вашого переліку vs макет; також прогалини, видимі з дизайну.)_

| Очікуваний стан | Що є в макеті |
|-----------------|---------------|
| Порожня форма | **Є** (Empty): неактивна кнопка, підказка про обов’язкові поля. |
| Валідна форма | **Є** (Filled & valid), з PDF і без окремої картки «валідна **без** файлу». |
| Помилки полів | **Частково:** окремі картки для **невірного телефону**, **email/порожніх обов’язкових**; немає окремих карток для **порожнього телефону**, **короткого повідомлення**, **занадто довгого імені/тексту**. |
| Завантаження | **Є** (Uploading): прогрес вкладення PDF. Немає стану «відправляємо **без** файлу» / загальний спінер без відсотків. |
| Неправильний тип файлу | **Є** (Wrong file type) з прикладом `.jpg`. |
| Завеликий розмір файлу | **Є** (File too large), кнопка submit неактивна. |
| Успіх | **Є** (Success): подяка + строк відповіді + «Write another message». |
| Видалення вкладення | **Частково:** кнопка **Remove attachment** / **Видалити вкладення** на live-формі (разом із «Change file»), **без** окремої картки в довіднику й без макету «після видалення». |

**Додаткові стани, яких не видно на макеті:**

- Валідація **лише одного** поля за раз vs **усі помилки після submit** разом.
- **Порожній / неповний телефон** (без `+`) vs **інші** помилки формату телефону (занадто короткий, невідомий код країни).
- **Мінімальна / максимальна довжина повідомлення** — жодного тексту помилки.
- Вкладення **обрано, але ще не перевірено** (проміжний стан між вибором і «PDF ready to send»).
- **Збій під час upload PDF** (окремо від «Could not send» всього повідомлення).
- PDF **рівно 5,0 MB** (межа) — показано лише 7,4 MB (відхилено) і 1,8 MB (ок).
- **Декілька спроб** після Error: чи залишається банер помилки.
- **Стан після «Write another message»** — порожня форма чи з попередніми даними.
- **Мобільна** верстка та довгі імена файлів / повідомлень (обрізання, переноси).
- **Українська** для кожного стану помилки й успіху (окремі макети).
- Взаємодія **без JavaScript** / з повільним інтернетом (тільки сценарій «тимчасовий зв’язок»).
- **Одночасно** помилка файлу і помилка полів (пріоритет відображення).
- **Після Remove attachment:** порожнє поле вкладення, текст підказки («Attach a PDF» / «Оберіть PDF»), чи лишається **активною** кнопка надсилання.
- **Change file vs Remove attachment:** різниця для користувача (заміна одразу vs спочатку очистити).

## Ризики

_(AI-аналіз: видимі з дизайну для бізнесу та приймання; без технічних порад.)_

| Ризик | Чому видно з макету |
|-------|---------------------|
| **Невідповідність очікувань по телефону** | Дизайн акцентує `+` і код країни; інші правила (маска, країни, довжина) на макеті **не показані** — ризик суперечностей із поточною формою та AC. |
| **Обіцянка строку відповіді** | «Reply within **three working days**» може стати **публічним зобов’язанням**, якщо фонд не готовий його дотримувати для всіх звернень. |
| **Юридичний текст згоди** | Нова формулювання згоди й «being contacted» може **не покривати** зберігання телефону й PDF, якщо політика сайту не оновлена. |
| **Втрата довіри при Error** | Фраза «nothing was lost» без винятків — ризик, якщо в реальності **частина даних** (наприклад, файл) не зберігається. |
| **Різний досвід успіху / помилки** | Успіх ховає форму; при помилці форма лишається — користувачі можуть **не зрозуміти**, чи звернення дійшло. |
| **PDF 5 MB «на межі»** | Без макету для **точно 5 MB** можливі суперечки «фонд обіцяв прийняти», а продукт відхиляє. |
| **Блокування submit через файл** | При завеликому файлі кнопка **вимкнена** — користувач може не зрозуміти, що проблема саме у вкладенні, якщо не прочитає текст під полем. |
| **Необов’язкове вкладення vs очікування фонду** | Підказка про партитури й листи дослідників **стимулює** прикріплювати файли; якщо процес опрацювання не готовий — навантаження на команду. |
| **Лише англомовні еталони станів** | Якщо uk **не погоджений** паралельно — ризик різних формулювань і довжини текстів на продакшені. |
| **Розбіжність із поточним сайтом** | Інші назви полів (Full name, Send message), інший текст згоди й успіху — ризик **розриву бренду** та перекладної когерентності з `/uk` і `/en`. |
| **Довідник станів на проді** | Якщо нижній блок «Reference Overview» потрапить на бойовий сайт — плутанина для відвідувачів (це **демо-навігатор**, не користувацький сценарій). |
| **Відсутність станів для тексту повідомлення** | Без дизайну мінімуму/максимуму — ризик **непогоджених** повідомлень (надто короткі або надмірно довгі) і різних правил між дизайном і специфікацією. |
| **Функція без вимоги (Remove attachment)** | Кнопка з’явилась у дизайні, але **не зафіксована** в AC Дня 2 і **не перевірена** окремим станом — ризик scope creep або пропуску в тестах/прийманні. |

**Що перевіряли (листопад 2026):** [прототип Figma Make](https://match-daily-72208179.figma.site/) — усі стани Preview; зріз **accessibility tree**; вибірковий **контраст** (обчислення з computed styles у прототипі); огляд **розмірів** кнопок. Бойовий `ContactForm` згадується як еталон імплементації, де вже є прийнятні патерни.

**Як читати класифікацію на refinement**

| Клас | Що означає для команди |
|------|------------------------|
| **Blocker** | Без рішення в дизайні/AC користувачі з клавіатури або SR **не зможуть** пройти сценарій або порушаться вимоги приймання публічної форми. |
| **Important** | Працюватиме частково; є бар’єри або невідповідність WCAG/UX — потрібна специфікація до релізу. |
| **Minor** | Поліпшення, прототип-артефакт, або вже покрито в коді при правильній імплементації. |

### Контраст кольорів (помилки та стани)

| ID | Спостереження (макет) | Орієнтир WCAG | Клас | Питання на refinement |
|----|------------------------|---------------|------|-------------------------|
| A-01 | Текст помилок полів / PDF (`rgb(139, 43, 32)` на фоні сторінки) — **~7,55:1** при 14px | AA ≥ 4,5:1 | **Minor** | Зафіксувати токен «error text» у DS; не світлішити в інших станах. |
| A-02 | Допоміжний статус 12px (`Complete all required…`, `Uploading… 68%`) — **~6,29:1** | AA ≥ 4,5:1 | **Minor** | Чи лишаємо 12px для статусу, чи піднімаємо до 14px для запасу контрасту. |
| A-03 | **Disabled Send message** (текст `rgb(95,102,98)` на `rgb(220,216,206)`) — **~4,14:1** | AA ≥ 4,5:1 для звичайного тексту | **Important** | Підтягнути disabled-стиль: темніший текст або інший фон; або **large text** ≥18px з 3:1 — узгодити з DS `Button`. |
| A-04 | Поле з помилкою телефону: **рожевий фон** + `aria-invalid` + червоний текст | Не покладатися лише на колір | **Minor** | Добра комбінація; зафіксувати в макеті як «error field» (фон + рамка + текст). |
| A-05 | Неактивна мова **Українська** на тому ж екрані — **~2,30:1** | AA для UI-тексту | **Important** | Окремо від форми, але на сторінці контактів — підправити toggle (не лише форма). |

### Екранні читачі (повідомлення про помилки)

| ID | Спостереження | Ризик для користувача | Клас | Рекомендація для макету / AC |
|----|---------------|----------------------|------|------------------------------|
| SR-01 | **PDF type/size:** `role="alert"` з текстом помилки — оголошується | Низький | **Minor** | Зберегти **один** патерн `alert` для помилок вкладення. |
| SR-02 | **Помилка телефону:** текст помилки **в accessibility name поля** + окремий рядок унизу (дублювання) | Довге оголошення, можливе повторення | **Important** | Label стабільний; помилка лише через **`aria-describedby`** на helper (як у MUI `helperText` у коді). |
| SR-03 | **Message:** при заповненні в **ім’я поля потрапляє весь текст листа** | Навігація SR ускладнена | **Important** | Accessible name = «Message»; значення — у `value`, не в `aria-label`. |
| SR-04 | **Помилка відправки (Error):** заголовок + абзац **без стабільного `role="alert"`** у live-формі (на відміну від PDF) | Користувач може не почути оновлення | **Important** | Банер = **`role="alert"`** або **`aria-live="assertive"`** один раз після submit. |
| SR-05 | **Uploading 68%:** лише текст, **`role="progressbar"` / `aria-valuenow` немає** | Прогрес неочевидний для SR | **Important** | Додати в макет-нотатку: `progressbar` + текстовий дубль; **`aria-live="polite"`** при зміні %. |
| SR-06 | Рядок «Complete all required fields…» **не прив’язаний** до disabled submit | Неочевидно, чому кнопки немає в tab order | **Important** | `aria-describedby` на submit → id статусного тексту (навіть коли кнопка disabled). |
| SR-07 | Підказка телефону в **звичайному label** (довгий приклад `+380…`) | Зайве на кожному фокусі | **Minor** | Підказку в **description**, не в ім’я поля; на макеті показати обидва стани (hint vs error). |

### Навігація клавіатурою

| ID | Спостереження | Клас | Що узгодити |
|----|---------------|------|-------------|
| K-01 | **Вибір файлу:** у DOM **`input[type=file]` 1×1 px**; зона — **`readonly` textbox** «Supporting document Choose PDF» | **Blocker** | У проді: видимий **`button`** «Choose PDF» + прихований file input; **не** текстове поле `readonly`. |
| K-02 | **Choose PDF** у порожньому стані **не окрема кнопка** в a11y-дереві (злите ім’я з textbox) | **Blocker** | Окремий фокусований елемент з тими ж стилями, що на візуалі. |
| K-03 | **Remove attachment** — кнопка в дереві, але **Change file** часто лише текст у блоці | **Important** | Обидві дії — **кнопки** або один «Change file» з доступним іменем. |
| K-04 | **Disabled submit** не фокусується (стандарт HTML) | **Important** | Дублювати причину в **видимому + описаному** статусі (див. SR-06); не підміняти disabled на `aria-disabled` без політики. |
| K-05 | Чекбокс у прототипі **`readonly`** (Empty / Filled) | **Blocker** *(прототип)* | На refinement: це **артефакт демо**; на проді чекбокс **завжди** toggle з клавіатури. |
| K-06 | Порядок tab: **8+ chip Preview** перед полями форми | **Minor** *(прототип)* | На проді chips **немає**; вимога: логічний порядок полів → файл → згода → submit. |
| K-07 | **Success:** нова розмітка без вимоги **перенести фокус** на заголовок подяки | **Important** | AC: після успіху фокус на **h2** «Thank you…»; **Write another message** — наступний tab-stop. |
| K-08 | Посилання **privacy policy** в довгому label чекбокса — окремий tab-stop | **Minor** | Очікувано; переконатися, що порядок: чекбокс → link логічний у макеті uk/en. |

### Рух і анімація

| ID | Спостереження | Клас | Рекомендація |
|----|---------------|------|--------------|
| M-01 | У прототипі багато **CSS transitions**; **прогрес %** імовірно оновлюється | **Important** | У AC/дизайн-нотатці: **`prefers-reduced-motion`** — статичний % або без анімованої смуги. |
| M-02 | Немає макету **без** відсоткової анімації | **Minor** | Один кадр «reduced motion» для розробки. |

### Що вже є в коді — перевикористати при імплементації

_(Не вимоги до Figma, а аргумент на refinement «не вигадуємо заново».)_

- **Помилки полів:** MUI `TextField` + `helperText` / `error` + іконка в `ContactForm.styles.ts` — відповідає макету, якщо не дублювати текст у label (SR-02).
- **Чекбокс:** нативна клавіатура + `FormHelperText` для помилки згоди.
- **Модальний успіх:** `ModalComponent` — керування фокусом при відкритті (якщо продукт лишає модалку замість inline success).

### Підсумок для слайду refinement

| Клас | Кількість |
|------|-----------|
| **Blocker** | 3 (K-01, K-02, K-05*) |
| **Important** | 14 |
| **Minor** | 11 |

\*K-05 — blocker **прототипу**; на проді очікується виправлення в реалізації, але макет має показувати **інтерактивний** чекбокс.

**Топ-5 питань власнику форми / дизайнеру**

1. **Файл:** підтвердити патерн «кнопка Choose PDF + прихований input», не textbox (K-01, K-02).
2. **Помилки:** один стандарт — `aria-describedby` для полів, `role="alert"` для PDF і submit error (SR-02, SR-04).
3. **Uploading:** `progressbar` + `aria-live` (SR-05, M-01).
4. **Disabled submit:** контраст і зв’язок із текстом статусу (A-03, SR-06).
5. **Success / Error:** куди йде фокус після зміни view (K-07).

**Обмеження аналізу:** прототип ≠ фінальний HTML сайту; контраст на проді перевірити після імплементації в темі фонду; українські стани форми в прототипі **не всі** прогнані voice-over — запланувати окремий прогін uk перед релізом (**Minor**).
