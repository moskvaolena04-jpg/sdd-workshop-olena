**Джерело (однакова для всіх):** «Хочемо, щоб відвідувачі могли підписатися на новини Фонду електронною поштою. Підписку треба легко скасувати.»

|--------|----------------------------|-------------|---------------------------|----------------------------------------|
| **A. BA story** (простий пакет історій) | ★ **Критерії приймання, історія 1:** немає місця підписки, полів, підтвердження; **Given/When/Then** одразу вимагають сценарій, якого у вимозі немає | Формальні ID (FR/RULE), constitution, юридичний блок як окремий модуль, явна matриця RULE→тест; «чому зараз» і метрики не запитує — **ховає** порожнину problem/ROI | Зв’язок **двох історій** із одним бекендом/ESP; «легко» без метрики; AC з **TBD** не доводяться до коду без повторного refinement | **Product** (історії, розмова на refinement); **AI** (короткий narrative + AC); інженерам — старт, але **без ID** слабка простежуваність |
| **B. GitHub Spec Kit** | ★ **Product brief → Проблема** і таблиця **метрик успіху:** вимога лише про «хочемо можливість», без болю та вимірювання; порожній brief видно **раніше**, ніж FR | Детальний покроковий UX і ролі після підписки (лише стрілки `текст`, без mermaid-учасників); модульність пакета; винятки в BR у нашій чернетці майже порожні — **ховає** edge cases | **FR-01/FR-02 → сигнал приймання** (обидва TBD); дублювання **C-01/C-02** vs **FR/BR** без єдиного ключового слова; **Q «що блокує»** без власників у шаблоні | **Product** (brief, non-goals, constitution як «обіцянки»); **AI** (чіткі розділи brief→spec); інженерам — **Must** і Q з прив’язкою до FR, але сигнали приймання треба домовляти окремо |
| **C. OpenSpec / BMAD** | ★ **Модуль 5 — CON-01 (юридичне / політика)** і **DEP-01..02** при email-підписці; паралельно **Модуль 3** — актор «система» і всі кроки в діаграмі **TBD** | Короткий «людський» pitch (немає єдиного абзацу problem story); легко **прогледіти** метрики бізнесу, бо SC без цифр і сигналів TBD | У стартовій чернетці **матриця RULE→AC/тест** порожня — формат *розрахований* на простежуваність, але без заповнення матриці важко довести **RULE-03 «легко»** до перевірки | **Інженери** (RULE, sequence, ID пакета); **AI** (модулі з ID); **Product** — місія (модуль 1), але UX тоне в TBD діаграмі |

## Короткий висновок для refinement

- **Найраніше про продуктову невизначеність:** Spec Kit (**проблема / метрики**).  
- **Найраніше про сценарій для розробки:** BA story (**AC підписки**).  
- **Найраніше про compliance і залежності:** OpenSpec/BMAD (**CON/DEP і потік**).

Жоден формат не замінює інші: з однієї короткої вимоги всі три природно дають багато **TBD**; відрізняється **де саме** команда **вперше** зупиняється та що залишається непоміченим, якщо заповнювати лише «зручний» розділ.

## Рефлексія (воркшоп)

| Формат | Що формат дозволив **приховати** при першому проході |
|--------|------------------------------------------------------|
| BA story | Відсутність problem statement і метрик |
| Spec Kit | Порожні потоки між системами (лише один рядок тексту) |
| OpenSpec / BMAD | Відсутність заповненої matриці простежуваності при наявних RULE |
