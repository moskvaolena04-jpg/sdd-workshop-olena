## 1. Постановка проблеми

**Кого** це стосується?  
Відвідувачів сайту фонду, які надсилають звернення через сторінку контактів (та пов’язані місця з тією ж формою — див. Q-12, RULE-28). Працівників фонду, яким потрібен вузький доступ до збережених звернень (див. NFR-02, RULE-16).

**Який** біль чи можливість?  
Зараз телефон можна не заповнювати, файлу немає; відповідь API не зберігає звернення. Потрібно посилити форму: обов’язковий телефон, необов’язковий PDF до 5 МБ, збереження звернення з обмеженням доступу й строку; сповіщення має відображати нове поле (посилання або завантаження).

**Чому зараз** (тригер, метрика, ризик)?  
Вихідний запит (issue #2): звуження форми контактів, обов’язковий телефон, вкладення CV/portfolio, оновлення сповіщень. Зараз телефон необов’язковий, файлу немає, відповідь не записує звернення в базу (`contact-form-feature.md`, §1).

**Метрика успіху** (підтверджено замовником): кожне прийняте звернення з телефоном і PDF-файлом до 5 МБ є в базі, його можуть відкрити лише 2 призначені працівники, запис не зберігається довше за 6 місяців; файл іншого типу або більший за 5 МБ у базу не потрапляє. _(Необов’язковість файлу без помилки — AC-15, RULE-17.)_

**User stories** (з `contact-form-feature.md`, §3):
- Як відвідувач, я хочу обов’язково залишити телефон і за бажанням прикріпити PDF, щоб фонд міг мені відповісти і переглянути документ.
- Як фонд, я хочу тримати весь запис лише в базі, не довше ніж 6 місяців від дати збереження і лише для двох працівників, щоб доступ до звернення лишався вузьким.

**Бажаний результат (одне речення):**  
Відвідувач на `/contacts` залишає обов’язковий телефон і за бажанням PDF до 5 МБ; прийняте звернення зберігається згідно з NFR-01–03 і RULE-16; сповіщення відображає вкладення (RULE-14, AC-08). Розбіжності UI з макетом — Q-15–Q-29.

## 3. Актори й потік

| Актор | Опис |
|-------|------|
| Відвідувач | Заповнює форму на сторінці контактів (і, за рішенням Q-12, у співпраці / вікні нот), ставить згоду, надсилає звернення |
| Форма контактів | Збирає поля, перевіряє на екрані, ініціює відправку |
| Перевірка | Клієнтська й серверна валідація (телефон, файл, інші поля) |
| Сховище | Зберігання прийнятого звернення та файлу за умовами RULE-16; місце зберігання байтів файлу — Q-08 |
| Сповіщення | Формується з даних звернення; для файлу — посилання або завантаження (RULE-14); отримувач — Q-13 |
| Призначені працівники (2) | Доступ до зчитування збережених звернень | Q-10 |

**Основний потік (щасливий шлях):**

```text
1. Відвідувач відкриває форму контактів, заповнює ім’я, email, обов’язковий телефон, повідомлення, згоду; за бажанням — PDF ≤ 5 МБ.
2. Форма і сервер перевіряють дані; при успіху звернення зберігається (телефон, дані, файл за наявності).
3. За наявності збереженого файлу формується сповіщення з посиланням або завантаженням (див. Q-07).
4. Відвідувач бачить підтвердження (поточна специфікація: вікно «Ваш запит надіслано» — RULE-13; макет: inline success — Q-23).
```

**Альтернативні / винятки:**

- Телефон порожній — запит не відправлено (AC-01, AC-04).
- Файл не PDF або більший за 5 МБ — файл не прийнято; чи зберігається звернення без файлу — Q-07; UI блокування submit — Q-21 (макет).
- Сервер відхилив запит після проходження форми — Q-06; макет: банер Error, форма з даними — Q-29.
- Невалідний телефон на екрані / на сервері — RULE-05, RULE-06, RULE-22, RULE-09, Q-03, Q-04, Q-05, Q-25.
- Успіх / помилка відправки: макет — різний UX (форма зникає vs лишається); Q-23, Q-29.
- Uploading, Change file, Remove attachment — на макеті; scope — Q-16, Q-22, Q-27.

_(Діаграма послідовності — `contact-form-feature.md`, § 4.)_
